## 2. 这一阶段的总体目标

本阶段不是单纯“把页面做出来”，而是把 AgentTrust 从合约闭环推进到一个可以被持续验证的完整本地 dApp：

1. 合约提供足够的只读索引，让前端刷新后能恢复交易和争议状态；
2. ABI 和部署地址不能靠手工复制，必须由 artifacts / broadcast 确定性生成；
3. 前端写操作必须正确处理钱包确认、交易回执、权限、网络和重复提交；
4. Trade 覆盖完整十状态流程，Disputes 覆盖 commit–reveal；
5. 正常交易和争议交易必须经过真实浏览器 + 本地 Anvil 验证；
6. Docker、CI、Pages 必须有部署完整性和只读模式门禁；
7. Base Sepolia 未部署前，不得把页面描述成可写的生产 dApp。

这证明 Pages 的“只消费成功 main CI”门禁正在正确工作，但也意味着合并后的完整主干门禁尚未闭环。

Contracts 当前已知失败步骤不是 build/test，而是：

```bash
forge coverage
```

错误：

```text
Stack too deep
Variable headStart is 1 slot(s) too deep inside the stack
```

Foundry coverage 会为准确统计临时关闭 optimizer 和 `viaIR`，从而触发栈深限制。GitHub 日志建议：

```bash
forge coverage --ir-minimum
```

### 下一位 Agent 的第一优先级

1. 从最新 `main@f9b3354` 创建新的 CI 修复分支，不要复用已经合并的 PR 分支。
2. 在 `contracts` 目录真实执行：

   ```bash
   forge coverage --ir-minimum
   ```

3. 如果成功，将 `.github/workflows/ci.yml` 中：

   ```yaml
   - run: forge coverage
   ```

   改成：

   ```yaml
   - run: forge coverage --ir-minimum
   ```

4. 如果仍失败，不要删除 coverage 门禁；应定位触发 stack-too-deep 的函数，或按 Foundry 当前版本支持方式拆分 coverage。
5. 本地重跑 Foundry、生成文件检查、前端测试/build 和 Playwright。
6. 提交到新的 follow-up 分支并创建新 PR。
7. 等待 Contracts、Frontend、Playwright、Docker 全部实际执行成功，再合并新的修复 PR。
8. 合并后确认 main CI 成功，随后 Pages workflow 应自动运行。

当前仓库允许在检查失败时合并，因此下一阶段必须以 GitHub Actions 的真实结果为准，不能把“已经进 main”理解为“已经验收完成”。

当前 Windows 环境没有可用 Docker Desktop，因此本机没有执行完整：

```bash

```

### 10.3 Docker 栈尚未跑完整浏览器业务流

目前：

- Playwright 主 E2E 使用原生 Anvil + 静态服务器；
- Docker job 独立验证 Compose、nginx、四合约、持久化复用和 stale bytecode 拒绝。

二者都覆盖了核心风险，但还没有让完整注入钱包业务流直接指向 Compose 内的 nginx/frontend。若后续要求更强的容器级端到端门禁，可增加一个 Compose-targeted Playwright 模式。

### 10.4 MetaMask smoke 未在本机跑通

这不是 dApp 失败。MetaMask smoke 已配置为 Linux `workflow_dispatch` 手动、非阻塞 job；下一步可在 GitHub Actions 手动触发验证。

### 10.5 Base Sepolia 没有部署

`deployments/84532.json` 当前故意为 `undeployed`：

### 10.6 尚未做生产审计

当前是研究 / MVP / 本地验证状态：
